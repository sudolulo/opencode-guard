commit, build, install or SDK publication is authorized by this document.

Supersedes for now: the deleted-ID reclamation part of
[native freshness draft](file:///home/dev/opencode-guard/docs/superpowers/specs/2026-10-13-native-permission-freshness-design.md).
Per-root generations, the RootAdmission service, NativeRuntime/DatabaseIdentity handles, prompt

## Problem (verified in source)

- Modern create accepts an explicit `input.id` and only short-circuits while a row with that ID
  exists (`packages/core/src/session.ts:209-211`). After deletion removes the row
  (`packages/core/src/session/projector.ts:257-258`) the same ID can be created again.
- Native keeps a closed run gate for a deleted ID only for the life of the instance state
  (`packages/opencode/src/session/run-state.ts:73` clears gates on disposal); an absent gate counts
  as open (`run-state.ts:103,135`). So a same-ID recreate after instance reload, restart or on
  another host is indistinguishable from the original by ID alone.
- Guard therefore keeps every deleted root ID for the life of its process
  (`lib/lifecycle.js`), and `admit()` creates map entries for any ID it is asked about. That is
  unbounded growth and was never accepted as final cleanup.

## Native contract

1. Every session row has an immutable `incarnationID: string`, generated by native core when the
   resource is created. It is not derived from the session ID or the clock alone; use the same
   opaque random ID helper style as other native IDs.
2. Exposure: read-only field on the V1 `SessionInfo` (`packages/schema/src/v1/session.ts`) and the
   v2 `Session.Info` (`packages/schema/src/session.ts`), so legacy `session.get` and v2
   `session.get` both return it. Optional in the schema only for decoding events and rows written
   before the migration; every row after migration has one.
3. Assignment: core `create` and legacy `createNext` put a fresh value in the `Created` event info.
   Fork, import, restore and any other new resource get a fresh value, never a copied one. The
   projector `Created` insert uses the event's value; if a replayed historical event lacks one, the
   projector generates one (rebuilt databases therefore get new incarnations, which fails closed for
   old bindings).
4. Immutability: no create/update/patch input can set or change it. The `Updated` projector path and
   legacy patch never write the column.
5. Migration: add the column and backfill every existing row with a unique generated value in the
   same migration, following the repo's migration generator conventions.
6. Owned-effect precondition: legacy and v2 session abort and delete accept an optional
   `incarnationID`. When supplied and it does not equal the current row's value, the call does
   nothing and fails with a distinct conflict error (HTTP 409, named error), not 404. Missing row
   stays 404. Omitted parameter keeps today's behavior.
7. Capability: `GET /experimental/capabilities` adds `sessionIncarnation: 1` only when 1-6 are in
   place.

## Guard contract

- When the host advertises `sessionIncarnation: 1`, every deferred guard effect (escalation retry,
  approval wakeup, background promotion, resume) binds `{ sessionID, incarnationID }` captured when
  the work was created, never re-read at execution time. Before the effect, the current
  `incarnationID` from the authoritative session read must equal the bound one; a mismatch or 404
  drops the work as stale.
- Lifecycle state is created only by real root activity, never by a read such as `admit()`. On an
  observed deletion the root's tokens close as today; the deleted record is then removed instead of
  retained, because stale work is rejected by its bound incarnation.
- Host without the capability: keep today's fail-closed retention unchanged. Do not loosen.
- Legacy event shapes (`permission.asked` `properties.id`, flat SDK calls) are unchanged.

## Workflows contract

Feature-owned child cleanup records the child's `incarnationID` at ownership establishment and
passes it to delete/abort when the host advertises the capability. A 409 means the ID now names a
different resource: record it, do not retry, do not delete.

Endpoint inventory: native legacy currently has delete and abort; v2 currently exposes interrupt
but NO delete. No new v2 delete endpoint has been implemented or authorized. The phrase “legacy and
v2 session abort and delete” in the native contract is unresolved scope mapping, not evidence that
every endpoint exists. Guard resume currently does not bind incarnation; source review has NOT
established a stale destructive continuation, so this remains a contract/evidence question. Native
compare/action atomicity was not an accepted risk. Holden selected the [incarnation-bound cleanup repair](file:///home/dev/opencode-guard/docs/superpowers/specs/2026-10-13-incarnation-bound-cleanup-design.md): atomic checked row/history cleanup plus captured runtime cancellation/finalizers, with [serialized source/test implementation plan](file:///home/dev/opencode-guard/docs/superpowers/plans/2026-10-13-incarnation-bound-cleanup.md). This is required option-B bound work, not authorization for full RootAdmission; source/test acceptance remains held until implemented, tested and independently reviewed.

## Tests required

- Native: explicit-ID recreate after delete gets a different incarnation; update/patch cannot change
  it; fork gets a fresh one; migration backfills unique values; abort/delete with a stale
  incarnation return 409 and leave the new resource untouched; omitted parameter unchanged.
- Guard: stale escalation/wakeup bound to an old incarnation is dropped after same-ID recreate;
  deleted roots no longer accumulate; `admit()` on an unknown ID creates no state; old host keeps
  retention.
- Workflows: cleanup with a mismatched incarnation does not delete the recreated session.
